# Notification Daemon

## Introduction

A notification daemon is the desktop component responsible for receiving and presenting application notifications to the user.

Rather than generating notifications itself, the daemon acts as a service that displays messages produced by applications and other desktop components.

In a modular desktop architecture, the notification daemon operates independently from both the compositor and the applications that request notifications.

---

## Why This Component Matters

Modern desktop applications frequently communicate important information without requiring immediate user interaction.

Examples include:

- completion of long-running tasks;
- incoming messages;
- software updates;
- connection status changes;
- battery warnings;
- authentication requests.

Without a notification daemon, applications may still generate notification requests, but there is no desktop service responsible for presenting them to the user.

A notification daemon provides a consistent mechanism for displaying these messages while preserving the separation between applications and the desktop environment.

---

## Responsibilities

A notification daemon is responsible for:

- receiving notification requests;
- presenting notifications to the user;
- managing notification lifetime;
- handling notification replacement and updates;
- providing a consistent notification interface across applications.

Its responsibility ends once the notification has been presented or dismissed.

Applications remain responsible for deciding when a notification should be generated.

---

## Architecture

Desktop applications do not communicate directly with the notification daemon.

Instead, notifications are typically delivered through the desktop notification service defined by the Freedesktop ecosystem.

This architecture allows applications to remain independent of any specific notification implementation.

A simplified interaction can be represented as follows:

```text
Application
        │
        │ Notification Request
        ▼
Desktop Notification Service
        │
        ▼
Notification Daemon
        │
        ▼
User
```

This separation allows different notification daemons to be substituted without requiring changes to the applications themselves.

---

## Relationship with Hyprland

Hyprland intentionally does not include a notification daemon.

As a Wayland compositor, its responsibility is limited to managing windows and the graphical session.

Notification management is delegated to an independent desktop component selected by the user.

This design follows the same modular philosophy applied throughout Project Kintsugi.

---

## Design Considerations

When evaluating a notification daemon, Project Kintsugi considers technical characteristics rather than visual appearance.

Relevant considerations include:

- compliance with desktop notification standards;
- native Wayland compatibility;
- active upstream maintenance;
- documentation quality;
- configuration model;
- resource usage;
- long-term maintainability;
- availability through approved Fedora package sources.

The objective is to select a notification daemon that integrates cleanly into the desktop architecture while maintaining a clear separation of responsibilities.

---

## Separation of Concerns

A notification daemon is not:

- a status bar;
- a desktop shell;
- a system logger;
- a window manager;
- a messaging application;
- a task scheduler.

Its sole responsibility is to present notification requests generated by other components of the desktop environment.

Maintaining this separation simplifies both the system architecture and long-term maintenance.

---

## Project Kintsugi Perspective

Project Kintsugi considers the notification daemon to be an infrastructure service rather than a user-facing application.

Although notifications improve the desktop experience, the primary objective is to introduce a standards-based service that enables desktop applications to communicate information in a consistent and modular manner.

This approach reinforces the project's emphasis on interoperability, maintainability, and clearly defined component responsibilities.
