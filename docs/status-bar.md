# Status Bar

## Introduction

A status bar is the desktop component responsible for presenting system and session information in a persistent graphical interface.

Rather than providing core desktop functionality itself, a status bar serves as an aggregation point for information generated by other components of the operating system and desktop session.

In a modular desktop architecture, the status bar is an independent component that can be selected, configured, and maintained separately from the compositor and the services that provide the information it displays.

---

## Why This Component Matters

A modern desktop session consists of multiple independent services operating simultaneously.

Users often need immediate access to information such as:

* the current workspace;
* the active window;
* the current time and date;
* network connectivity;
* audio status;
* battery level;
* system resource usage.

Without a status bar, this information would either be unavailable or require launching separate applications to inspect individual system states.

A status bar provides a centralized and continuously visible interface while preserving the modularity of the underlying desktop architecture.

---

## Responsibilities

A status bar is responsible for:

* displaying session information;
* presenting the status of desktop components;
* visualizing information obtained from external services;
* providing a consistent location for desktop indicators;
* optionally exposing user interactions through individual modules.

Its primary responsibility is presentation rather than system management.

---

## Separation of Concerns

A status bar is not:

* a window manager;
* a desktop shell;
* a notification daemon;
* a network manager;
* an audio manager;
* a clipboard manager;
* a system monitor.

Although many status bars include interactive modules, these modules act as interfaces to external services rather than implementing those services themselves.

Maintaining this separation simplifies the desktop architecture and improves long-term maintainability.

---

## Relationship with Hyprland

Hyprland intentionally does not include a status bar.

This design reflects its philosophy as a Wayland compositor rather than a complete desktop environment.

Instead, users are free to select a status bar that best matches their workflow and architectural requirements.

Most modern Wayland status bars communicate with Hyprland through its inter-process communication (IPC) interface to obtain workspace information, active window data, and other session state.

This loose coupling allows both components to evolve independently.

---

## Design Considerations

When evaluating a status bar, Project Kintsugi considers technical characteristics rather than visual appearance.

Relevant considerations include:

* native Wayland compatibility;
* integration with Hyprland;
* modular architecture;
* active upstream maintenance;
* documentation quality;
* configuration model;
* dependency footprint;
* long-term maintainability;
* availability through approved Fedora package sources.

The objective is to select a status bar that integrates cleanly into the desktop architecture without assuming responsibilities that belong to other components.

---

## Project Kintsugi Perspective

Project Kintsugi considers the status bar to be a presentation layer rather than a system service.

The information displayed by the bar originates from the operating system, the compositor, or dedicated desktop services.

The status bar simply provides a structured and continuously accessible interface for presenting that information.

This distinction reinforces the project's emphasis on modularity and clear separation of responsibilities.
