# Notification Daemon Selection

## Objective

The purpose of this document is to select the notification daemon that will become the standard notification service for Project Kintsugi.

Rather than selecting a solution based on popularity or visual appearance, the decision follows the project's engineering principles and long-term desktop architecture.

The selected notification daemon should integrate naturally with Hyprland while remaining lightweight, maintainable, standards-compliant, and available through the project's approved package sources.

---

## Background

Project Kintsugi has successfully established the core components required for a functional graphical desktop, including the compositor, terminal emulator, application launcher, file manager, and status bar.

The next step is to introduce a notification service capable of presenting desktop notifications generated by applications and other system components.

The notification daemon should operate independently while integrating seamlessly with the existing desktop architecture.

---

## Evaluation Criteria

The selected notification daemon should satisfy the following requirements:

- Compliance with the Freedesktop Desktop Notifications Specification.
- Native Wayland compatibility.
- Active upstream maintenance.
- High-quality documentation.
- Predictable configuration.
- Availability through the project's approved package sources.
- Low resource usage.
- Long-term maintainability.
- Clear separation of responsibilities.

The objective is not to maximize visual features, but to select a reliable infrastructure component that integrates cleanly into the desktop environment.

---

## Candidate Notification Daemons

### Mako

Mako is a lightweight notification daemon designed specifically for Wayland compositors.

It focuses exclusively on desktop notifications while maintaining a small dependency footprint and straightforward configuration.

Its design philosophy closely matches the modular architecture adopted throughout Project Kintsugi.

---

### Sway Notification Center

Sway Notification Center extends the traditional notification daemon model by incorporating a persistent notification history and interactive notification center.

It provides additional desktop functionality while remaining compatible with Wayland environments.

Its broader feature set introduces additional complexity compared to simpler notification daemons.

---

### Dunst

Dunst is one of the longest-established notification daemons in the Linux ecosystem.

Although originally developed for X11 environments, it also supports Wayland through modern compositor protocols.

Its maturity and stability make it a well-known alternative, although its architecture originated before Wayland became the standard desktop protocol.

---

## Fedora Evaluation

Project Kintsugi will verify:

- package availability;
- package source;
- maintenance status;
- installation complexity;
- compatibility with Fedora 44.

Preference will be given to solutions available through the project's approved package sources.

---

## Decision

Project Kintsugi selects Mako as the standard notification daemon.

The decision is based on the project's engineering principles rather than feature count.

Mako satisfies all mandatory evaluation criteria while providing a focused implementation that aligns with the project's modular desktop architecture.

---

## Rationale

Mako was selected because it provides an appropriate balance between simplicity, standards compliance, maintainability, and Wayland integration.

The decision is supported by the following observations:

- available from the official Fedora repositories;
- native Wayland implementation;
- focused single-purpose design;
- active upstream maintenance;
- straightforward configuration;
- low resource usage;
- long-term maintainability.

Its narrow scope closely matches Project Kintsugi's preference for components with clearly defined responsibilities.

---

## Trade-offs

Every notification daemon represents a balance between:

- simplicity;
- functionality;
- configuration complexity;
- resource usage;
- ecosystem maturity;
- long-term maintenance.

Project Kintsugi documents these trade-offs explicitly rather than assuming any implementation is objectively superior.

Selecting Mako intentionally favors a focused notification service over a more feature-rich desktop notification center.

---

## Future Review

The notification daemon selection may be revisited if:

- Fedora packaging changes significantly;
- upstream maintenance changes;
- another implementation provides a substantially better engineering balance;
- or the project's desktop architecture evolves in a way that changes the original requirements.

Until then, Mako will remain the standard notification daemon for Project Kintsugi.

---

## Validation on Fedora 44

The candidate notification daemons were evaluated against the package sources available on Fedora 44.

### Mako

Mako is available from the official Fedora repositories.

It is actively maintained, Wayland-native, and implements the Freedesktop notification specification.

---

### Sway Notification Center

Sway Notification Center is available from the official Fedora repositories.

It combines a notification daemon with a persistent notification center and notification history.

Although this broader feature set may be advantageous for some desktop environments, Project Kintsugi currently prefers a notification daemon with a narrower and more clearly defined responsibility.

---

### Dunst

Dunst is available from the official Fedora repositories.

It remains a mature and well-maintained notification daemon, although its historical focus on X11 makes it a less natural architectural fit for a Wayland-first desktop.

---

## Conclusion

Desktop notifications are a fundamental infrastructure service within a modern graphical desktop.

After evaluating the available alternatives, Project Kintsugi adopts Mako because it provides the most appropriate balance between standards compliance, native Wayland support, maintainability, and alignment with the project's modular engineering philosophy.

Validation confirmed that Mako integrates correctly with the Fedora 44 user session through D-Bus activation, allowing Project Kintsugi to adopt the upstream integration model without introducing additional compositor-specific startup configuration.
