# Authentication Agent

## Introduction

An authentication agent is the desktop component responsible for presenting authentication dialogs when applications or system services require elevated privileges.

Rather than implementing authentication itself, the agent provides the graphical interface through which users authorize privileged operations requested through the PolicyKit (Polkit) authorization framework.

In a traditional desktop environment, an authentication agent is typically started automatically as part of the desktop session.

In a compositing window manager such as Hyprland, the authentication agent becomes an independent component that must be selected, integrated, and maintained separately.

Understanding this distinction is essential for building a modular desktop environment.

---

## Why This Component Matters

Many graphical applications perform operations that require administrative privileges.

Examples include:

* mounting removable storage devices;
* modifying network configuration;
* managing printers;
* changing system settings;
* installing or updating software.

Without an authentication agent, these operations may fail silently or be unable to present the user with an authentication dialog.

As a result, the desktop remains functional but lacks an essential mechanism for performing privileged graphical operations.

---

## Responsibilities

An authentication agent is responsible for:

* receiving authentication requests from Polkit;
* presenting authentication dialogs to the user;
* collecting user credentials when required;
* returning the authentication result to Polkit.

Its responsibility ends once the authentication request has been completed.

Authorization policy, privilege management, user accounts, and application behavior remain the responsibility of other system components.

---

## Relationship with Polkit

Authentication agents operate as graphical front-ends for the PolicyKit authorization framework.

Polkit determines whether an operation requires authorization and delegates user interaction to an authentication agent.

The agent itself does not define authorization rules or security policies.

Instead, it provides a standardized user interface that allows users to approve or deny authentication requests generated by Polkit-aware applications and services.

---

## Relationship with Hyprland

Hyprland intentionally does not include an authentication agent.

This follows the compositor's philosophy of providing window management functionality without bundling higher-level desktop services.

Users are therefore free to select an authentication agent that best fits their desktop architecture.

Project Kintsugi evaluates this component independently in accordance with its engineering methodology.

---

## Design Considerations

When selecting an authentication agent, Project Kintsugi considers several technical characteristics, including:

* compatibility with Polkit;
* native Wayland compatibility where applicable;
* active upstream maintenance;
* predictable behavior;
* simplicity of integration;
* availability within the Fedora ecosystem;
* long-term maintainability;
* clear separation of responsibilities.

The preferred solution should integrate naturally with the desktop while remaining focused on a single responsibility.

---

## Separation of Concerns

An authentication agent is not:

* an authorization framework;
* a privilege escalation utility;
* a desktop environment;
* a system service manager;
* or a security policy engine.

Its sole responsibility is to provide the graphical interface required for user authentication during privileged operations.

Maintaining this separation of responsibilities simplifies desktop architecture and improves long-term maintainability.

---

## Project Kintsugi Perspective

Project Kintsugi considers the authentication agent a fundamental infrastructure component rather than a user-facing feature.

Although the desktop can operate without one, a complete graphical environment requires a mechanism for handling privileged operations in a consistent and standards-compliant manner.

For this reason, the authentication agent will be evaluated and selected using the same engineering methodology applied throughout Phase 1.
